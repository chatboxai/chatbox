# Architecture Notes

For agents, not humans. Non-obvious, hard-won engineering knowledge. Add an entry whenever you discover or fix something a future agent would otherwise have to rediscover the hard way (see `AGENT_RULES.md` End-of-Task Checklist item 2). Don't remove an entry unless the underlying issue is genuinely gone from the code.

## Current Architecture

- The root renderer route uses `MantineProvider`, MUI `ThemeProvider`, `NiceModal.Provider`, and global error boundaries.
- `routes/__root.tsx` has function `creteMantineTheme` (upstream typo preserved) that configures Mantine colors, typography, spacing, radii, and component defaults.
- `globals.css` defines CSS variables for light/dark modes. Many components depend on these variable names.
- The main shell uses a persistent/temporary `SwipeableDrawer` sidebar depending on screen size.
- Chat pages are built from `Header`, `MessageList`, `InputBox`, and `ThreadHistoryDrawer`.
- Mobile, RTL, safe-area, and desktop window-control behavior already exist. Preserve unless intentionally removing mobile/web support.
- Background images can be configured globally or per session; root route renders `BackgroundImageOverlay` for root/session pages.
- Chat orchestration is a single streaming loop, not a multi-step agent loop: `src/renderer/stores/session/orchestration.ts` builds context + tools once per turn and calls `model.chatStream()`, which wraps the `ai` SDK's `streamText()`. The AI SDK's internal loop (not WorkspAIce code) handles any multi-round tool-call/tool-result exchange within that single call.
- Tools are assembled in `src/renderer/stores/session/tools-builder.ts` from MCP (`src/renderer/packages/mcp/controller.ts`), web search, file access, knowledge-base/session-attachment RAG, sandbox, and skills (`src/renderer/packages/skills/controller.ts` → `src/main/skills/ipc-handlers.ts`).
- Models that don't support native tool-use get a "legacy tool fallback" (`legacy-tool-fallback.ts`) that runs web/KB search via prompt engineering before the model call, as a separate code path from native tool-use. Skills have no equivalent fallback for non-tool-use models.
- **Tool errors have one channel: throw (FABLE §6.3).** Every renderer toolset (MCP, web search, KB, session-attachment RAG, file, sandbox, skills) reports infrastructure failures by throwing an `Error`; the AI SDK v6 converts the throw into a `tool-error` stream part, forwards the message to the model (`output-error` content), and continues the step loop — the old MCP-controller comment claiming throws break the stream predated the v6 upgrade. `normalizeToolSetErrors` in `tools-builder.ts` is the assembly-boundary safety net: it wraps non-Error throws and converts returned `Error` values into throws (a returned Error JSON-serializes to `{}`, so the model saw nothing); aborts pass through untouched. The persisted tool-part error shape is `{error: string, errorCode?: number, input, toolName}` in BOTH `stream-chunk-processor.ts` and `abstract-ai-sdk.ts` — keep them in sync, `ToolCallPartUI.extractToolError` expects `error` to be a string. Operation *outcomes* stay values, not errors: a skill script's `{success:false, stdout, stderr, exitCode}` and sandbox_bash's cancelled `{exitCode:130}` are results the model needs to read.
- `@mastra/*` (`core`, `rag`, `libsql`) is used only for RAG/reranking (`src/shared/models/rerank.ts`, knowledge-base/session-attachment vector DB and chunking), not for orchestration.
- **Skills reach the model via two independent paths.** (1) Model-driven: `tools-builder.ts` injects `<available_skills>` XML + `load_skill`/`execute_skill_script` tools — but regular chat `orchestration.ts` does NOT pass `enabledSkillNames` to `buildToolsForSession` (only `taskSessionActions.ts` does), so this path is effectively task-mode-only. (2) Deterministic `/slash`: the composer records `invokedSkills` on the user `Message`; `orchestration.ts` `buildInvokedSkillInstructions()` re-loads each SKILL.md body fresh (via `skills:load`) and appends it to the system instructions for that turn, so an explicitly-invoked skill always runs. Bodies are re-loaded (not stored on the message) so editing a skill affects regenerations.
- **`src/main/skills/gray-matter.d.ts` is a hand-rolled stub** declaring only `matter(input)` — no `.stringify`. To write a SKILL.md (e.g. `skills:create`) build the frontmatter string directly (quote+escape the description for YAML); don't call `matter.stringify`.

## Known Risk Areas

- `InputBox.tsx` is very large and behavior-heavy. Prefer localized, visual changes unless refactoring with tests.
- Renaming app IDs/protocols can break installed-app behavior, deep links, settings paths, and local data. This is acceptable in the fresh fork unless the user asks for migration.
- Mobile support exists via Capacitor. Preserve if not intentionally dropping mobile builds.
- RTL and safe-area behavior exists. Preserve unless intentionally redesigning supported platforms.

- **electron-builder + pnpm dependency collector (ROOT CAUSE of recurring `Cannot find module` crashes — fixed via patch).** electron-builder 26 picks a node-modules collector based on detected package manager. Because the repo is a pnpm workspace (`packageManager: pnpm` + `pnpm-lock.yaml`), it used `PnpmNodeModulesCollector`, which runs `pnpm list --prod --json --depth Infinity` and trusts that output. `pnpm list --json` **deduplicates/collapses repeated subtrees** (e.g. `electron-store > conf > ajv` is emitted with empty `dependencies`), silently dropping ~149 transitive packages (`fast-deep-equal`, `fast-uri`, `@emotion/*`, `@babel/*`, `function-bind`, `get-intrinsic`, etc.) from the asar → runtime `Cannot find module` crashes. **Fix:** `patches/app-builder-lib@26.8.1.patch` makes `out/util/appFileCopier.js` try the **NPM** collector first (`const pmApproaches = [PM.NPM, <detected>, PM.TRAVERSAL]`). electron-builder's `NpmNodeModulesCollector` runs `npm list` (keeps a `_dependencies` field on every node) and back-fills deduplicated subtrees from a name@version cache, collecting the complete tree from `release/app`'s flat npm install (created by `ensure-app-deps.cjs`). It also tolerates the mis-declared `@types/*` runtime deps that `ensure-app-deps` strips. Asar grew 463 → 574 packages. **This patch is pinned to `app-builder-lib@26.8.1` — re-verify on any electron-builder upgrade.** Re-verified working with Electron 42 (2026-07-02). Upstream later landed its own pnpm-collector dedup fix (electron-builder PR #9618, ≥~26.13; latest 26.15.3) that repairs the *pnpm* collector instead of forcing the NPM one — evaluating an electron-builder upgrade + patch drop is a tracked follow-up in `STATE.md`, not something to do casually mid-task.
- **macOS single-architecture packaging.** `electron-builder --mac --arm64` does not constrain the build while `electron-builder.yml` lists both `arm64` and `x64` under `mac.target.arch`; it finishes arm64 and then starts x64. For an arm64-only build, also override the config (`-c.mac.target.arch=arm64`) or temporarily narrow the YAML architecture list. Interrupting after the arm64 DMG completes still leaves a partially packaged `release/build/mac/` x64 app that must not be installed.
- **pnpm 10.33 ignores the `pnpm` field in `package.json`.** Patch/override/onlyBuiltDependencies config must live in `pnpm-workspace.yaml`, not `package.json`.
- **npm (release/app) does NOT honor pnpm `overrides` → version-coupled packages must be exact-pinned in `release/app/package.json`.** `ensure-app-deps.cjs` runs `npm install` in `release/app`, which ignores pnpm `overrides` in `pnpm-workspace.yaml`. Example: caret ranges let npm pull `@mastra/libsql@0.13.8` (peer `@mastra/core >=0.15.3 <0.16`) against pinned `@mastra/core@0.13.2`, causing `TypeError: Class extends value undefined`. **Fix:** `@mastra/core`/`@mastra/libsql`/`@mastra/rag` are exact-pinned (`0.13.2`/`0.13.2`/`1.0.8`) in `release/app/package.json` to mirror the pnpm overrides. Any future version-coupled dependency must be exact-pinned the same way, not just overridden in `pnpm-workspace.yaml`.
- **General coupling note.** Always run `pnpm install` at the workspace root after changing `package.json`, `pnpm-workspace.yaml`, or `release/app/package.json`. With the NPM-collector patch, missing transitive deps no longer need to be added manually to `release/app/package.json`.
- **node-fetch@2 is stripped from the packaged app at pack time — do not re-add it (SEC-5).** `.erb/scripts/patch-mastra-rag.cjs` (called from `ensure-app-deps.cjs`, the beforePack hook, after `npm install`) rewrites `release/app/node_modules/@mastra/rag/dist/index.cjs` to lazy-require `zeroentropy` (its only consumer, `ZeroEntropyRelevanceScorer`, is never used — WorkspAIce reranks via Cohere directly), strips zeroentropy from the installed manifest, and deletes the package. `release/app/package.json` has `"overrides": {"node-fetch": "3.3.2"}` so the one residual declared dependent — the `@mastra/core`→otel→GCP-detector→`gaxios` chain, which never loads (verified 0 modules in a packaged startup probe) — gets the CVE-fixed ESM-only v3 instead of v2; if that unreachable path ever loaded it would crash loudly rather than ship vulnerable code. Rules: (1) bumping `@mastra/rag` makes the patcher **hard-fail** packaging on unknown structure — re-verify the zeroentropy require and update `patch-mastra-rag.cjs` (and re-run the packaged startup module probe) as part of any such bump; (2) don't re-add `node-fetch`/`whatwg-url`/`tr46`/`webidl-conversions` to `release/app/package.json` — they were pre-NPM-collector-era manual pins; (3) dev/vitest intentionally run the unpatched workspace `@mastra/rag` (eager zeroentropy in dev is harmless; the CVE concern is shipped code).
- **IPC channel allowlist.** The preload bridge (`src/preload/index.ts`) validates all `invoke()` calls against `src/shared/ipc-channels.ts` (105 channels). Any new `ipcMain.handle` registration must also be added to `INVOKABLE_IPC_CHANNELS` in `ipc-channels.ts` or it is blocked at the bridge.
- **MCP stdio spawn is gated by a native approval ledger (SEC-1).** `mcp:stdio-transport:create` runs a local process, and the renderer is untrusted (webSecurity off), so `src/main/mcp/approval-ledger.ts` fingerprints each launch over `{command, args, config-env}` (NOT the merged shell env, which is main-derived and would cause spurious re-prompts) and shows a native confirm dialog for any fingerprint not already in `{userData}/mcp-approved-servers.json`. Approve → recorded → silent next time; editing command/args/env is a new fingerprint → re-prompt. The dialog is the trust anchor: it stays necessary even now that webSecurity is re-enabled (SEC-3, done), because it also defends the still-renderer-writable settings blob. The renderer threads a display-only server name through `IPCStdioTransport.create(params, {name})`; the name is cosmetic (fingerprint ignores it). Do not add a code path that spawns stdio bypassing `ensureStdioServerApproved`.
- **Config encryption key.** `config.json` is encrypted at rest via electron-store + `safeStorage`. The OS-keychain-protected key is stored at `{userData}/.config-key`. If deleted/corrupted (e.g. macOS keychain reset), the store regenerates a new key and re-encrypts — the old encrypted data becomes unreadable. Advise users not to delete `.config-key`.
- **The config store must not be touched before app 'ready' (Electron ≥42).** `safeStorage.isEncryptionAvailable()` returns `false` pre-ready on Electron 42 (it returned `true` pre-ready on 35, macOS). A keyless store would not only skip encryption — with `clearInvalidConfig: true` it would *wipe* an existing encrypted `config.json`. `src/main/store-node.ts` is therefore lazily initialized: `initStore()` is the first call inside `app.whenReady()` in `main.ts`, the exported `store` is a delegating proxy, and any pre-ready access throws loudly instead of silently degrading. If you add main-process code that reads settings during bootstrap (module scope, `open-url`, early events), it must wait for ready first. The KB/RAG worker loops tolerate the throw (catch + 3s retry).
- **Electron ≥42 does not download its binary at install time** (postinstall removed for supply-chain reasons; the dist downloads on first *bin* run). electron-vite and Playwright `_electron` spawn the binary path directly, so `.erb/scripts/postinstall.cjs` runs `node_modules/electron/install.js` when `dist/` is missing. Related: pnpm's `minimumReleaseAge: 10080` makes Electron releases invisible for 7 days — when bumping majors, pick the newest version older than a week (43.0.0 was 2 days old and thus blocked when 42.5.0 was chosen, 2026-07-02).
- **webSecurity is ON; all cross-origin renderer HTTP goes through the main-process net proxy (SEC-3).** The desktop renderer's global `fetch` is replaced at boot (`src/renderer/setup/net_proxy_fetch.ts`, imported in `index.tsx` before app code) and forwards cross-origin http(s) requests over `net-proxy:fetch`/`read`/`abort` IPC to `src/main/net-proxy.ts` (pull-based body streaming; `session.defaultSession.fetch`, so the user proxy setting applies). Rules this creates: (1) renderer code using `fetch`/`ofetch`/ai-SDK-default fetch is covered automatically, but **EventSource, WebSocket, XHR, and Web-Worker fetches are NOT proxied** and will fail same-origin/CORS — don't use them for cross-origin calls. (2) CSP `connect-src` is `'self' data: blob:` (+ `localhost:1212` in dev); a renderer-direct cross-origin fetch fails even before CORS. (3) The proxy accepts http/https only — `ses.fetch` could otherwise read `file://` and custom schemes on the renderer's behalf. (4) Programmatic `file:` reads (fetch/XHR) from the packaged `file://` document are cancelled in `onBeforeRequest` in `main.ts` — Chromium treats file→file as same-origin and would otherwise allow arbitrary local-file reads even with webSecurity on; static assets (scripts/styles/images/fonts) still load. (5) FormData/ReadableStream request bodies throw (`net-proxy: unsupported request body type`) — no call site uses them today; add serialization if a feature needs it.
- **Mobile SQLite encryption** — `storages.ts:109` still uses `'no-encryption'`. SQLCipher for Capacitor is a follow-up pending the mobile-support decision.
- **Freshly packaged (ad-hoc-signed) builds can hang at startup on a silent macOS Keychain prompt — use `--use-mock-keychain` for automated probing.** Every repackage produces a new ad-hoc code signature, which invalidates the Keychain ACL on the "WorkspAIce Safe Storage" entry; `initStore()`'s `safeStorage` read then blocks the main thread in `SecItemCopyMatching` waiting on an access-control prompt (no window, CDP endpoint mute, `Runtime.evaluate` never returns — confirmed via `sample <pid>`). Interactive launches just show the prompt; automated/Playwright launches of the packaged binary must pass `--use-mock-keychain` (Chromium flag; isolates from the real keychain, no prompt). Never "fix" this by deleting the keychain entry — the user's real installed app depends on it (see the `.config-key` note above).
- **Local Electron E2E works in the current desktop environment.** `pnpm qa:ci` can launch Playwright `_electron` locally; the 7 deterministic Electron scenarios passed on 2026-06-29. Keep CI as the cross-platform authority because headless environments may still lack a usable Electron display.
- **`pnpm dev:web` is not browser-only.** It serves the renderer at `http://localhost:1212`, but `electron-vite dev` also starts Electron and uses the normal app `userData` unless `WORKSPAICE_E2E_USER_DATA_DIR` is set. Do not use it for isolated QA without an explicit temporary user-data directory; the Playwright E2E fixtures already set one.
- **biome-ignore-all directives** — 4 files suppress `noExplicitAny` blanket. Narrowing to per-line suppressions is a low-priority cleanup. `settingsStore.ts` also suppresses `noFallthroughSwitchClause` for the migration switch.
- **Biome gates: repo is 0-errors and ratcheted — keep it that way.** `qa:biome` checks only files changed vs `origin/dev` (including unstaged!), so run it with a clean tree, and remember that any repo-wide `biome check --write` puts every touched file into that gate — the repo was brought to 0 error-level diagnostics precisely so this can't fail. `qa:biome-ratchet` (in `qa:ci`) additionally fails if repo-wide `summary.errors`/`summary.warnings` rise above `scripts/qa/biome-baseline.json`; after intentionally reducing warnings run `pnpm qa:biome-ratchet --update-baseline`. The ratchet parses biome's `--reporter=json` `summary` counts — never the `diagnostics` array (it includes non-error/warning entries and truncates).
- **CSP has two delivery paths — the packaged one is a build-time `<meta>` tag, NOT the header (SEC-8).** `onHeadersReceived` header injection never applies to the packaged window: it loads via `loadFile()` (`file://`), and injected response headers are ignored for `file:` responses — before 2026-07-03 the packaged app ran with **no CSP at all** while the header looked correct in dev. Production CSP is injected by `injectDesktopProdCsp()` in `electron.vite.config.ts` (desktop builds only — web/mobile fetch providers directly and `connect-src 'self'` would break them); the header in `main.ts` covers dev/HMR. **Keep the two policies in sync.** Rules: (1) prod `script-src` has NO `'unsafe-eval'` but needs `'wasm-unsafe-eval'` — shiki's oniguruma engine compiles WebAssembly for code highlighting; any new renderer dep using `eval`/`new Function` will break in packaged builds only. (2) The meta tag must be the FIRST tag in `<head>` (last head-prepend plugin wins), before any script. (3) `frame-ancestors` can't be delivered via meta — header-only. (4) E2E loads the built renderer over `file://`, so the zero-console-error E2E scenarios regression-test the prod CSP on every `qa:ci`. (5) **Testing gotcha:** DevTools-initiated code (Playwright/Puppeteer `evaluate`, `executeJavaScript`, console) temporarily permits eval, including in synchronously-injected inline scripts — a CSP eval probe must run from an async page script (`setTimeout` inside an injected `<script>`) or it will falsely report eval as allowed.
- **All external URL opening must go through `src/main/open-external.ts`** (`openExternalSafe`, allowlists `http:`/`https:`/`mailto:`, logs+drops the rest). `shell.openExternal` deliberately has no other call site — keep it that way when adding links/menus/OAuth flows, and extend the allowlist consciously if a new scheme is ever needed (FABLE_REVIEW SEC-4).
